# MiniGPU labs

## 组织与边界

这是一个逐步完成同一套代码的项目型 lab，不复制十套 starter，不提供核心算法答案。每周只提交本周可运行增量。10 周完成全部必做交付；第 11–12 周用于补齐验收或一项可测量的改进，每人每周仍为 6–8 小时。

| 固定负责人 | 长期负责 | 互审重点 |
| --- | --- | --- |
| A | 数学 / MVP、顶点准备、CUDA kernel、分块和剔除 | 审 B 的覆盖、深度、数据及实验是否与 GPU 约定一致 |
| B | framebuffer / CPU 光栅化与深度、OBJ、正确性、benchmark / profiling | 审 A 的坐标、内存、并发和计时边界 |

共享类型、CLI 和构建入口以小 PR 协作：A 修改 GPU 相关部分，B 修改输入输出和测量部分。每周由模块负责人实现，对方 review；不让双方同时重写同一算法。遇到超时，先缩小场景和输入支持，保持三后端、正确性与报告的交付闭环。

## 统一接口与正确性约定

第一周在代码注释中锁定以下规则，后续修改需双方 review。

- 数学使用列向量，变换顺序 `clip = P * V * M * position`；右手系，相机朝 -Z，裁剪空间采用 `-w <= x,y,z <= w`。
- framebuffer 原点左上，x 向右、y 向下；像素中心为 `(x+0.5, y+0.5)`。viewport 映射以宽高为边界，包围盒 clamp 到有效像素索引。
- 深度由 NDC z 映射到 `[0,1]`，清屏为正无穷，较小值通过。等深时按输入三角形顺序取先出现者；禁止依赖线程竞争决定结果。
- CPU/GPU 共享 winding、退化三角形判定和 top-left 覆盖规则；基础颜色用屏幕空间重心插值，透视正确颜色插值作为可选扩展。
- 为控制工时，必做版本不实现完整齐次裁剪：任一顶点不在裁剪体内的三角形整体丢弃；必须先检查有限值和 `w > 0`，再透视除法。明确记录因此会在边界产生缺面，展示场景保持完整入镜。
- OBJ 最小子集为 `v` 与正数、从 1 开始的三角形 `f` 顶点索引。可读取 `v/vt/vn` 中的顶点字段并忽略材质、法线、UV；负索引、非三角面和越界索引明确拒绝，空行与注释可跳过。无顶点颜色的网格采用确定性配色。
- CPU 与 CUDA 复用主机端变换结果。Naive kernel 每个线程拥有一个像素，顺序遍历全部三角形，独占该像素颜色和深度；避免一开始引入深度原子操作。
- 后端最终统一为 `cpu`、`cuda-naive`、`cuda-tiled`。图像对比至少验证背景 / 覆盖和 RGB 最大误差，建议色差阈值 1/255；深度绝对误差阈值从 `1e-5` 起，并记录实际容差和原因。失败必须返回非零退出码。

## 周计划

表中工作量为**每人**的预算，包含学习、实现、验证和互审。验收是这一周应补充的测试，不是 starter 已具备的能力。

| Lab | A：数学与 GPU | B：CPU 与实验 | 当周验收 / 产物 | 每人 |
| --- | --- | --- | --- | --- |
| 01 · 像素与契约 | 实现最小向量 / 矩阵运算，锁定坐标与屏幕顶点格式 | 熟悉 framebuffer / PPM，建立颜色、尺寸、输出错误检查 | 可读背景图；单位矩阵、平移、图像大小验证；接口 review | 6–8h |

| 09 · Tiled Renderer | 实现 triangle–tile 包围盒相交剔除、tile 索引与遍历 | 复跑一致性及端到端测量，检查空 tile / 边界 / 大三角形 | Tiled CUDA Renderer；至少一个代表性场景稳定改善；同时报告回退场景 | 6–8h |

| 11 · 可选 / 缓冲 | 未达标则补齐；已达标则只尝试 shared memory 或布局中的一项 | 对照测量改进，判断收益是否超过复杂度 | 未优化成功也保留实验结论；主线始终可运行 | 6–8h |

## 分块的最小实现

第 9 周允许先在 CPU 用三角形屏幕包围盒生成 tile 候选列表，再上传 CUDA；不要求并行 binning。每个 tile 用 offset/count 指向连续的 triangle index 数组，保留输入顺序以保证等深一致性。分配容量随实际候选数量增长，禁止固定上限静默丢三角形。每像素只遍历所属 tile 的候选列表。报告分别测量 binning、上传和 kernel，并标明这个实现是 CPU binning + GPU rasterization。

若 kernel 变快但端到端退化，必须如实报告，并在缓冲周检查静态场景复用或 tile 粒度；不能仅删除预处理时间来声称整体加速。

## Lab 提交与最终验收

每个 PR 包含：完成的任务、关键规则、可直接执行的验证命令、结果或图片、已知限制、另一人的 review。每周优先增加小型针对性用例，避免为尚未实现的算法写永远通过的占位测试。

最终 CLI 应接受后端、模型、分辨率和输出路径，benchmark 应支持重复次数和 CSV 路径；在实现相应 lab 时加入，starter 不预埋未使用的配置系统。所有后端必须对相同输入使用相同变换和配色。

最终检查顺序：干净目录配置 Release → CPU 测试 → CUDA 测试 → 三后端渲染固定模型 → 自动图像 / 深度比较 → benchmark → 用报告复现一项性能结论。把实际命令写入最终 README。

展示材料至少包含三角形插值、遮挡 cube、一个来源和许可清楚的三角化 OBJ；仓库自带 cube 用于基础验收。benchmark 的大规模场景可以由确定性网格重复生成，记录种子、真实三角形数、可见比例，避免只通过离屏三角形制造虚假加速。
